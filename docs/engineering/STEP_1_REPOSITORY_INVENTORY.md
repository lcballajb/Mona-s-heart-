## Documentation/code contradictions and stale claims

1. ADR-002 says the PostgreSQL dependency could not be vendored and the reference server only uses an in-memory repository, but `pg`, `PostgresStore`, the adapter factory, migrations, and PostgreSQL tests now exist. The ADR is historical/stale and should be superseded or annotated rather than used as current architecture evidence.
2. The background-jobs document calls the bounded PostgreSQL worker “future,” while `server/worker.mjs`, `server/worker-entry.mjs`, durable claim/retry methods, a worker image, and worker tests are present. Production operation is still unverified, but implementation is no longer wholly future.
3. The API reference says a request-correlation response header does not exist, while the server sets `x-request-id` on responses. Contract documentation is stale even though a formal OpenAPI/error contract remains missing.
4. PostgreSQL setup and ADR-004 require separate migration and runtime roles, but neither migrations, bootstrap automation, Compose, nor CI creates/verifies that split; CI migrates and tests with `mona_test`. This is an intended control documented as if operational guidance, not an implemented privilege boundary.
5. System documentation describes actor/organization transaction context for RLS-sensitive operations, but ordinary Postgres store CRUD methods do not consistently wrap calls in actor-context transactions, and the routed API does not expose most such operations. The design exists; end-to-end enforcement does not.
6. Documentation describes provider-neutral production services and health coverage, but the API constructs health without storage or scanner providers and production adapters remain uninjected. Architecture artifacts must not be read as deployed controls.
7. Prior maturity scores and “verified baseline” language are snapshots at older commits and explicitly lack deployment/GitHub evidence. They are not proof of current `origin/main` or production readiness.
